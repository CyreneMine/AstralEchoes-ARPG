## Q1 事件和每帧读取怎么选

> 处理"玩家死亡"，你在 `PlayerCombat` 和 `PlayerObject.Update` 里每帧读 `Health.isDead`，在动画和 `EnemyAI` 脱战上又用了 `OnPlayerStateChange` 事件。同一件事为什么用两种方式？你判断的标准是什么？

**用户回答**

> 判断标准是是否是自己本身的操作。比如每帧读取的两个地方都是玩家自己身上的脚本，而使用订阅事件的地方都是其他地方需要被通知已经发生了这件事后要执行的其他地方的事件。

**点评**

这个标准和代码有两处冲突：

- `PlayerObject` 是玩家自己的脚本，却订阅了事件，在 `ChangeState` 里切动画、重置 `isAttacking`；
- `EnemyAI` 属于"别的地方"，却在 `CheckPlayer` 里每帧读 `isDead`。

实际在起作用的标准是：

- **持续性的判断，每帧读状态**：例如"现在死了吗，死了就不能移动、攻击、侦测"；
- **变化那一刻只做一次的反应，用事件**：例如切动画、重置攻击状态、怪物脱战，以后的死亡界面。发布者不需要知道谁在关心，以后加接收方也不用改 `PlayerHealth`。

**追问准备**：事件的缺点是什么？调用关系不直观、排查更难；忘记取消订阅会出问题；订阅方之间的执行顺序不能依赖。

## Q2 订阅放在哪个生命周期

> `EnemyAI` 在 `OnEnable/OnDisable` 里订阅和取消订阅，`PlayerObject` 却放在 `Awake/OnDestroy`。为什么两处不一样？如果敌人也改成 `Awake` 订阅、`OnDestroy` 取消，以后接入对象池会出什么问题？

**用户回答**

> 对象池里面不一定会将对象进行 Destroy，如果这样做的话会导致 EnemyAI 这个脚本不能正常取消订阅，里面的代码会出现重复执行。

**点评**

- "回收时不 Destroy"说对了，但这种写法的后果不是"重复执行"。Awake 只执行一次，只订阅一次。真正的问题是：**被回收、已经隐藏的怪物仍然在收事件**。玩家一死，池里的怪物也会执行 `LoseTarget()`；如果里面调用了 NavMeshAgent，对未激活的 agent 调用 `SetDestination` 会报错。
- "重复订阅"出现在另一种写法里：OnEnable 订阅、OnDestroy 取消。每取出一次多订阅一次。
- 漏答了"为什么两处不一样"：玩家在场景里只有一个，生命周期和场景相同，不会进对象池，所以 Awake/OnDestroy 没有问题；怪物以后要进池，所以按启用和禁用配对。统一改成 OnEnable/OnDisable 也可以，而且更一致。

**追问准备**：Awake → OnEnable → Start 的执行顺序。当天的真实例子是：第一版在 Awake 订阅、在 OnEnable 取消，刚订阅就被取消了（见记录 33）。

## Q3 讲一个今天排查的 Bug

> 玩家复活的瞬间会被怪物打一下。请讲清楚：当时的现象；根本原因；为什么最后选择"死亡和复活时都让怪物脱战"，而没有用复活无敌时间或复活点。

**用户回答**

> 1. 现象：玩家在怪物面前死后，怪物会停止移动站在玩家面前，然后玩家复活的一瞬间就会被判定受到一次攻击掉血。
> 2. 根本原因是玩家死后 Time.time 还在正常计时，所以怪物的攻击 CD 也在正常走，而怪物本身没法再移动了，就一直在玩家面前。玩家一旦复活就会瞬间触发怪物的攻击。
> 3. 这是参考的业内其他游戏的方式，在玩家死后应该让怪物解除仇恨重新回到自己的巡逻去。复活点思路是打算后续接入的，这里暂时没有这么做。

**点评**

结构是六题里最好的。

- **原因可以说得更准确**：攻击冷却靠"上次攻击时间"判断。玩家死亡期间怪物不调用 `TryAttack`，但冷却时间照样在过；玩家原地复活时，怪物正好在攻击范围内，冷却也早已结束，所以复活后第一帧就出手。
- **建议补上排查过程**：
  - 第一次尝试在事件里设置 `isWaiting` 和 `waitUntil`，没有效果。原因有两个：复活时参数是 false，把 `isWaiting` 设回了 false；`Update` 先调用 `CheckPlayer`，再检查 `isWaiting`，攻击发生在等待判断之前。
  - 改成脱战以后又发现：去掉 `Update` 里的死亡判断后，怪物回到巡逻点，如果尸体还在侦测范围内，会重新追过去对着尸体出刀。于是在 `CheckPlayer` 开头补上了死亡检查。
- **第 3 点有风险**："参考业内其他游戏"会被追问"哪个游戏"。要么举一个自己玩过并确认过的例子，要么按取舍来讲：
  - **脱战**：处理根因，问题出在怪物的状态；可以复用现有的 `LoseTarget()`，改动很小；
  - **复活无敌时间**：只是推迟问题，无敌结束后怪物还站在原地；
  - **复活点**：依赖场景和存档点系统，目前还没有，计划之后接入。

## Q4 数据分层

> 你把角色数据分成了 SO 配置、存档里的等级和经验、`CharacterStats`、`CharacterHealth` 四层。
> 1. 为什么 `CharacterStats` 用普通 C# 类，而不是 ScriptableObject？
> 2. 如果直接在 SO 上改运行时数值，在编辑器里和打包后分别会出现什么问题？
> 3. 升级后当前血量保持不变、只限制在新上限以内，而不是回满或按比例换算，这是出于什么考虑？

**用户回答**

> 1. 因为这个类里面的值是需要通过计算来改变的，SO 文件更适合静态的、不变的那些配置项。
> 2. 直接修改 SO 的数值，会在编辑器里面保存下来，下一次在编辑器运行也会继续使用修改后的数值。如果是打包后，这种属性在运行时被修改了，重新启动后这个修改不会被保存下来。这也是为什么 SO 文件更适合拿来做配置。

（第 3 问未作答）

**点评**

- **第 1 问没说到关键**："需要计算"不是根本原因，SO 也能存计算结果。关键是 **SO 是共享资产**：引用同一个 SO 的对象拿到的是同一份数据，`Resources.Load` 返回的也是同一个实例。如果把属性写进 SO，同类型的十只怪会共用一份属性。运行时状态应该每个实例各有一份，所以用普通类，在 `Init` 里 new 出来。
- **第 2 问正确**，可以补两句：
  - 在编辑器里，改动会写进资产，可能被提交到 Git，测试值就混进了正式配置；
  - 打包后，这次运行期间所有引用它的地方都会读到改过的值，只是不写回磁盘。
- **第 3 问待重答**。这是设计取舍，没有标准答案，要说清楚各方案的优劣：
  - **回满**：升级的奖励感最强，但战斗中升级就等于免费回血；
  - **按比例换算**：玩家感觉平滑，实现更复杂，还有取整问题；
  - **保持当前值，只限制在新上限以内**：最简单、可预期，上限下降时也不会超出上限。
  - 最后补一句：以后想改成回满，只需要改 `UpdateStats` 这一处。

## Q5 扩展性

> `EnemyHealth.Dead()` 里直接调用了 `RewardMgr` 和 `MissionMgr`，`RewardMgr` 用 `switch` 按道具类型分发。假设下个版本要加成就统计、掉落物特效、击杀音效，还要新增五种道具类型，你会怎么调整这两处？今天为什么没有提前这样写？

**用户回答**

> 如果要新加成就统计，就需要新建数据类和成就配置 SO；新加特效、击杀音效，我会去新建专门管理特效和音效的管理器，然后在需要播放特效或者音效的地方使用管理器来进行统一执行。今天没有这么写是因为当前项目还在原型初期，还没有制作到特效音效这些部分。要新增道具类型，需要先去把枚举扩充，把五种类型都加进去，然后去 switch 里面分别添加它们的 case。

**点评**

六题里最弱，待重答。

- **没答到考点**：这题考的是耦合。现在每加一个"怪物死亡后要做的事"都得改 `EnemyHealth.Dead()`。回答讲的是新系统内部怎么做，没回答"它们怎么知道怪物死了"。
- **期待的方向**：
  - 把怪物死亡改成事件，例如 `OnEnemyDead(enemyId)`；奖励、任务、成就、特效、音效各自订阅，`EnemyHealth` 只负责广播，加功能不用改它（开闭原则）；
  - 主动说出代价：订阅方之间的执行顺序不能依赖，例如任务判定如果依赖经验已经加上，就要注意顺序。
- **"为什么今天没写"有更好的答案**：当时只有奖励和任务两个接收方，直接调用最清楚，约定出现第三个接收方时再改成事件（记录 34）。这是有意控制复杂度，比"还在原型初期"更能体现判断力。
- **道具类型的追问**：
  1. **结构**：消耗品、任务道具、材料其实都是"放进背包"，只有经验和金币需要特殊处理。switch 最后应该只剩少数特殊 case 和一个默认的"进背包"。类型很多时也可以用 `Dictionary<ItemType, 处理方法>`，由各系统自己注册。
  2. **枚举的坑**：Unity 按整数值序列化枚举，新类型插在中间会让已填的 SO 数据全部错位，应该加在末尾。这和当天"字段改名导致数据丢失"是同一类问题。
