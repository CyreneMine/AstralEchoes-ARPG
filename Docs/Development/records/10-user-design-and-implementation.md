## 一、从用户观察到方案调整

### 1. 用户先指出斜向参数变化与不流畅的关系

用户观察到：按住 Shift 和 WASD 转向时出现减速再加速，猜测两个键同时按下后，动画参数从 1 降到约 0.7 再回到 1，造成切换生硬。这是用户提出的现象与初步判断。

Codex 随后检查脚本和混合树，发现原混合树按方向分量区分走跑，动作都分布在 Y 轴。归一化的 W+D 输入两个分量各约 0.707，总长度仍为 1，直接使用 Y 分量确实可能使动画退回走跑混合。最初建议使用 1D 的速度参数，Idle/Walk/Run 对应 0/0.5/1。

### 2. 用户提出“持续跑动时保持原速度”的思路

用户在看建议代码前提出：检测角色此刻是否移动、是否按住 Shift 处于跑动状态；如果正在跑动，转向时保持原本速度。这是用户对期望行为与实现方向的主动设计。

Codex 分析：这一思路可实现，但直接“保持原值”可能误锁住刚起步的低速，或阻止走路切换跑步时加速。建议把速度大小和方向拆开：速度标量负责向 Walk/Run 目标速度平滑，转向另行计算。同一满幅度输入、同一走跑状态内换向时，目标速度自然保持不变。

### 3. 用户反馈第一次修改仍有问题，促使继续排查

用户反馈使用 magnitude 后仍不流畅，并指出代码为了平滑而让数值逐渐变化。再次检查发现，原实现仍通过 Vector2.MoveTowards 对整个速度向量插值；中间向量可能短于两端。例如 `(0,5)` 向 `(5,0)` 过渡，经过 `(2.5,2.5)` 时长度约为 3.54。

因此，“改动画取值”是第一阶段建议，不是完整解决方案。最终采用 float currentSpeed 独立平滑速度，并以平滑后的角色朝向乘 currentSpeed 得到普通移动向量。

用户随后归纳：一个变量只负责速度，方向独立计算，同一 Run/Walk 状态下转向只改变方向。用户还用“就像一根线”的比喻说明理解：线长表示速度，线朝向表示移动方向。Codex 澄清：问题来自向量平滑轨迹使中间长度缩短，不是归一化斜向输入本身会减速；也不是 Vector2 表达速度这件事本身错误。

### 4. 用户指出冲刺动作尚未结束就恢复位移

用户观察到冲刺动作还没结束，方向键已经推动角色。检查发现 dashTimer 只持续 0.2 秒，归零后普通移动恢复，而 isQuicking 尚未结束。Codex 最初提出区分冲刺位移阶段和收尾锁定阶段，并通过状态退出清理锁定。

这是针对“收尾前完全禁止普通移动”的候选方案，并非最终实际采用方案。

### 5. 用户进一步提出“过渡期间速度跟随动画”的目标

用户认为“中间过渡也是要时间的调起来很麻烦”，希望冲刺退出到移动时识别行走/跑步，使速度与过渡动作对应。这条意见明确了最终方案需要逐渐恢复控制，不能只等状态退出后切换速度。

Codex 据此提出动画曲线驱动的普通移动权重：冲刺为 0，普通动作侧为 1，借助 Animator 对同名曲线参数的混合，使代码使用的移动能力随动画过渡变化，避免另外维护一份恢复计时。

用户询问是否需要新建 Layer 再控制 Layer Weight。Codex 解释这是普通 Float 参数与片段曲线，不需要新建动画层，并给出配置和脚本读取方式。建议中使用的名字为 LocomotionWeight，用户实际实现选用了 MoveWeight，文档以实际工程名称为准。

### 6. 用户自行补充冲刺期间禁止转向

用户明确报告：在转向条件中加入是否处于冲刺的判断，使角色冲刺时停止转向。该补充由用户提出并实施，不能只写成助手给出的统一方案。

最新代码中的实际条件为：

```csharp
if (dashTimer <= 0f && hasInput && !isQuicking)
```

这一条件保留了“有输入且高速位移计时结束”的检查，同时要求整个冲刺标记已清除，防止收尾阶段普通输入改变角色朝向。

## 二、最新文件核验与用户实际采用的方案

用户本轮明确表示“我已经改完了”。本次只读检查确认以下修改已保存：

| 项目 | 当前已保存内容 | 依据 |
|---|---|---|
| 普通速度 | currentSpeed 为 float，按目标走跑速度平滑 | PlayerObject.cs |
| 普通移动方向 | transform.forward，与 currentSpeed 组合 | PlayerObject.cs |
| 走跑动画 | 1D，参数 Velocity；S_Idle=0、S_Walk=0.5、S_Run=1 | Cyrene.controller，按动作 GUID 核对 |
| 移动权重参数 | Float MoveWeight，默认值 1 | Cyrene.controller |
| 冲刺曲线 | S_QuickShift_F 的 MoveWeight 曲线，时间 0 和 1 的值均为 0 | 对应 FBX meta |
| 普通动作侧权重 | S_Idle/S_Walk/S_Run 没有额外 MoveWeight 曲线，使用参数默认值 1 | 三份 FBX meta 与 Controller |
| 权重读取 | Clamp01(animator.GetFloat("MoveWeight")) | PlayerObject.cs |
| 实际普通位移 | transform.forward * currentSpeed * moveWeight | PlayerObject.cs |
| 冲刺高速阶段 | dashTimer>0 时覆盖为 dashDirection * dashSpeed | PlayerObject.cs |
| 重力 | 普通水平移动权重计算后独立施加 vSpeed | PlayerObject.cs |
| 转向锁定 | 转向条件包含 !isQuicking | PlayerObject.cs，用户主动补充 |
| 冲刺结束通知 | 仍保留 StartQuick/EndQuick 事件机制；EndQuick 清除 isQuicking | 代码与冲刺 FBX meta |

用户采用的是“冲刺显式曲线 0 + 普通动作缺省权重 1”。早先建议为普通片段也添加常量 1 曲线；本次检查未发现这三条显式曲线，不把建议误写成用户实际操作。Unity 文档说明，片段缺少同名曲线时，与参数默认值混合，因此当前默认值 1 是此实现的一部分。

当前未发现采用 QuickExitBehaviour 的证据，不将此前状态退出方案写成最终实现。

核心实际代码：

```csharp
moveWeight = Mathf.Clamp01(animator.GetFloat("MoveWeight"));
Vector3 move = transform.forward * currentSpeed * moveWeight;
```

Velocity 表示普通走跑速度比例，MoveWeight 表示恢复普通位移的比例。没有将已经乘 MoveWeight 的实际速度反写到 Velocity，避免恢复过程中目标走跑动画又退回低速状态。

> 角色移动采用速度大小与朝向分别处理的方式，速度标量根据行走、跑步目标值平滑变化，角色朝向依据输入方向进行旋转。针对冲刺收尾与普通移动衔接的问题，使用动画曲线驱动的移动权重参数，将普通水平速度与动画过渡联系起来；冲刺片段提供零权重，普通动作侧使用参数默认值一，脚本读取混合后的参数缩放普通位移。与此同时，在普通转向条件中检查冲刺状态，限制冲刺期间的转向。相关方案经过问题反馈与多轮调整形成，后续仍需对实际过渡效果进行运行验证。
