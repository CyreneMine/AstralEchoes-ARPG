# 三选一临时 Buff 的设计讨论

日期：2026-11-23。工程版本：`e15cea6`。讨论对象：三选一临时 Buff（新增，Buff 管理器与 Buff 面板名称暂定）、`CharacterStats`、`CharacterHealth`、`PlayerObject`、`PlayerMgr`、`DialogueMgr` / `DialoguePanel`，以及主线副本的保存点与复活（新增）。

协助工具：Claude Code。

相关 Issue：#16（三选一临时 Buff，定稿设计写在该 Issue 的评论里）、#31（属性改为 float，生命上限按百分比保持）、#32（主线副本的进度保存点、复活次数与重置流程）、#17（场景切换与剧情推进）、#23（统一管理暂停的多个来源）。

本记录只整理设计讨论，**没有修改任何代码、配置、场景或预制件**。唯一改动的文件是剧情草案中关于 Buff 的一句话（见"实际采纳与用户调整"）。设计由用户完成，Claude Code 负责评估。

## 用户观察与目标

用户问还要完成哪些内容才能算原型完成。Claude Code 对照 AGENTS 中的最小闭环盘点后，建议先做三选一临时 Buff（#16）。用户决定先讨论 Buff。

Claude Code 在没有被要求的情况下直接给出了一整套设计方案（属性修饰项、Buff 组件、战斗节点等）。用户回复："我不看你给的方案，我自己来设计，然后你再评判评估。"这份方案**没有被采用**，用户也没有阅读，以下不再展开。之后按"用户提出设计、Claude Code 评估"的方式进行讨论。

目标是在实现前把 Buff 的职责划分、获得方式、效果计算、计时、死亡与存档规则定下来，开 Issue 后再由用户实现。用户另外说明，这个作品不仅是毕业设计，半个月后（约 12 月上旬）也会用作求职作品，所以工作量多一些也可以接受。

## 用户提出的想法

按讨论顺序记录：

1. **基本结构**：做一个独立的面板，用一个管理器控制。需要弹出选择界面时，在需要的地方调用管理器的开始方法，再通过 UIManager 生成面板，随机出 3 个 Buff。
2. **随机放在哪里**：UIManager 只负责生成面板，随机逻辑写在面板初始化里。
3. **已选记录**：面板会被销毁，但管理器不会，所以由管理器用数组记录选过的 Buff，面板初始化时读取管理器的数据。
4. **随机规则**：从 Buff 池里随机，只排除玩家选中的那一个。剩下不足 3 个时只显示剩下的；选项做成预制体动态生成，不足 3 个就少生成几个。
5. **测试可比性**：Claude Code 提出随机选项会影响论文中的对比测试，用户认为不同 Buff 的打法差异"选不同 Buff 就好了"。
6. **限时**：Buff 统一限时，到时间自动结束。用户同意把剧情草案中"持续到该战斗结束"改为限时。
7. **属性计算**：由 PlayerObject 统计和计算。原本的属性是白值，新加的统一用变量记录，再算出总值，用总值计算实际表现。
8. **百分比规则**：以白值为基底按百分比相加。例如攻击 10，获得两个 Buff 分别加 20% 和 30%，总值为 10 + 10×0.2 + 10×0.3。
9. **池子用完**：在管理器里留一个标记，没有可选的 Buff 时，显示类似"你已经足够强了"的提示文字（提示系统待做）。
10. **何时弹出**：效果上让玩家自己挑时机更好，但现阶段做成获得时强制选择。
11. **获得方式**：完成特定任务时给予选择次数；在剧情指定的地方获得选择次数，选完后直接销毁这个区域。这类区域只出现在剧情专属的桥段，只有在剧情阶段才能进入。Buff 次数不放进 `RewardMgr` 的奖励里，是一个独立的功能。
12. **对话中获得的次数**：在对话结束后再调用，不在对话中弹出。
13. **暂停**：Buff 面板打开时暂停。
14. **取整**：最好的方案是把属性改为 float。
15. **可加的属性**：攻击、防御、生命上限都能加。生命上限变化时以当前生命百分比计算，Buff 结束时也一样；之后升级也全部改为按百分比。
16. **死亡、复活与副本**：在副本（主线场景）里给玩家一定的复活次数。还有次数时，可以选择从最近的保存点复活，Buff 保留为该保存点保存时的状态；没有次数时死亡，Buff 消失，整个副本从头再来（选择 Buff 的区域恢复）。死亡时弹出死亡界面、时间停止，所以 Buff 也停止计时。
17. **不回溯的内容**：玩家死亡后，无论有没有复活次数，使用的道具和获得的经验都不回溯。
18. **任务进度与副本**：需要多次复活的情况只出现在主线副本里，平时的场景没有。主线副本只是某个任务的一个阶段，副本彻底结束才写任务存档。
19. **副本保存点**：一个副本按进度设若干个保存点（0、1、2、3），每到一个保存点就存盘，玩家彻底死亡时重置这份数据。如果在两个保存点之间获得了 Buff，还没到下一个保存点就退出，重进时从上一个保存点重新开始。
20. **获得范围**：所有能获得 Buff 的阶段都在副本里。即使是通过对话获得，也算副本中的额外奖励，副本外没有获得 Buff 的机会。
21. **副本结束**：副本结束时完全清除 Buff，已选列表也一起清空。
22. **采纳评估意见**：用户请 Claude Code 评价整套设计（"是不是烂透了"）。对于"由管理器决定选项"的建议，用户说"可以这么做，我觉得你说的很有道理"。论文中的表述留到写论文时再讨论。

## 辅助分析与建议

Claude Code 读过的文件：`CharacterStats.cs`、`CharacterHealth.cs`、`PlayerHealth.cs`、`PlayerMgr.cs`、`PlayerObject.cs`、`PlayerCombat.cs`、`EnemyCombat.cs`、`EnemyHealth.cs`、`DialogueMgr.cs`、`DialoguePanel.cs`，并检索了 `timeScale`、`SetCursorState` 和各管理器写盘的调用位置，以及 STATUS、剧情草案 V1 和当时未关闭的 Issues。

### 对结构的评估

- 管理器配面板的写法与现有的 `DialogueMgr` / `DialoguePanel`、`MissionMgr` / `MissionPanel` 一致；触发点只调用管理器，不需要了解界面细节。
- 按 STATUS 的记录，UIManager 关闭面板时会销毁面板，所以已选记录不能放在面板里。用户随后说明由管理器持有，这个问题解决。
- 指出随机逻辑放在面板里和常见做法不同：一般由逻辑层决定给出哪几个选项，界面只负责显示，这样方便测试和记录。用户采纳。

### 与现有代码的接入点

- `PlayerMgr.GetAtkValue()` 读的是 `player.Stats.Atk`；`CharacterHealth` 自己另存了一份 `def` 和 `maxHp`；`PlayerObject.UpdateStats()` 在升级时把白值传给生命组件。指出这三处都要改为使用总值，否则攻击类 Buff 不生效、防御类 Buff 不生效，或者升级时 Buff 被白值覆盖。
- 如果是百分比加成，白值在升级后会变化，总值需要在白值或 Buff 变化时重新计算，不能只算一次。
- 属性是 `int`，提出取整方式的问题。用户决定改为 float。
- `CharacterHealth.UpdateStats` 在上限变化时只限制当前血量不超过上限，升级也走这个方法。指出如果改成按百分比，升级的表现也会跟着变，用户决定升级也一起改为按百分比。

### 时序与暂停

- `DialogueMgr` 在交付对白 `InitData` 之后立即调用 `CheckFinishMission` → `FinishMission`，所以对话一开始任务就已经完成。如果此时强制弹出 Buff 面板，等对话关闭时，`DialoguePanel.HideMe` 的回调会恢复输入并锁住光标，而 Buff 面板还开着。用户说明次数不走奖励，并决定在对话结束后再调用。Claude Code 补充：`HideMe` 恢复光标的代码在淡出结束后的回调里，所以调用要放在这个回调之后。
- 任务面板、背包面板都是自己设置 `timeScale`，Buff 面板会成为又一个暂停来源（与 #23 有关）。
- 计时使用受 `timeScale` 影响的时间，面板打开和死亡界面期间 Buff 都会暂停。

### 被撤回的分析

- Claude Code 曾根据"任务、道具、经验都是变化即写盘"推断出两个冲突：一是任务阶段推进写盘而 Buff 没有写盘，二是复活时 Buff 回退而其他数据不回退。用户指出复活还没有做，这些是各系统自己的数据，和 Buff 及主线进度无关：道具和经验按设计本来就不回溯，任务进度在副本里只是一个阶段，副本结束才写盘。Claude Code 承认这两个冲突是把现有写盘方式和对设计的误解拼在一起推出来的，并非真实问题，予以撤回。

### 待补问题的提出

按讨论先后，提出过这些需要回答的问题：池子用完时怎么处理、拿到次数后何时打开面板、选择区域在重新加载后会不会再出现、哪些数据要写盘、死亡时 Buff 怎么处理、副本结束时保存点数据和剩余 Buff 怎么处理、已选列表是否随副本结束清空。用户逐一给出了上面"用户提出的想法"中的答案。

### 对整体设计的评价

用户问整套设计是不是很差，Claude Code 的评价：

- 生命周期完整，从获得到副本结束的每个时刻都有明确的规则；白值加百分比、属性用 float、生命上限按百分比保持，都是常见做法，答辩时容易说明。把获得范围限制在副本内，存档和清理都只需要在副本范围内处理。
- 风险主要在工作量：Buff 连带出 float 改造和副本系统。更正了之前"Buff 依赖前两个 Issue"的说法：Buff 的核心部分（选择、计时、属性计算）只依赖 float 改造，副本系统只需要它提供"恢复到某次保存"和"全部清空"两个操作。因此建议的顺序是 float（#31）→ Buff 核心（#16）→ 副本系统（#32）。
- 提醒论文中的口径：复活次数、保存点和全灭重来容易被看成独立的 Roguelite 模式，写作时应表述为主线关卡的挑战机制。

## 实际采纳与用户调整

定稿内容写在 #16 的评论、#31 和 #32 中，要点如下：

- **结构**：Buff 管理器持有 Buff 池、已选列表、剩余次数和"池子已空"标记；由管理器排除已选的 Buff 并随机出最多 3 个，传给面板（Claude Code 建议，用户采纳）；面板由 UIManager 创建，用预制体动态生成选项。
- **获得**：只在主线副本内获得，是独立功能；获得时强制选择，面板打开期间暂停；对话中获得的次数在对话面板完全关闭后再调用；剧情区域选完后销毁。
- **效果**：限时；可以加攻击、防御、生命上限；总值 = 白值 × (1 + 各百分比之和)，由 PlayerObject 计算；属性改为 float；升级和 Buff 导致的生命上限变化都按当前生命百分比保持。
- **副本**：任务阶段和副本进度分开。副本进度按保存点写盘；有复活次数时回到最近的保存点；没有次数时整个副本重置；道具和经验不回溯；副本结束时清除 Buff、保存点数据和已选列表。
- **待定**：复活次数的具体数值、副本外死亡怎么处理（#32）。
- **剧情草案**：`Docs/Design/世界观与主线剧情-V1.md`"制作设想"一节中，"效果持续到该战斗结束"改为"完成特定任务或到达剧情指定地点时获得选择次数……效果限时，到时自动结束"，并注明是 11-23 用户的调整。

未采用：Claude Code 第一次主动给出的整套设计方案。Claude Code 推测的两个存档时机冲突已撤回。
