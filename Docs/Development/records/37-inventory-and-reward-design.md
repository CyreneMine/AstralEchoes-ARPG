# 玩家持有道具、背包与任务发奖的设计讨论

日期：2026-11-16。工程版本：`6edf1b3`。讨论对象：玩家持有道具管理器（新增，名称暂定）、背包面板（新增）、`RewardMgr`、`MissionMgr`、`ItemDatabase` / `ItemConfig`、`RewardSlot`。

协助工具：Claude Code。

相关 Issue：#25（简单背包与道具表，设计定稿和参考类图写在该 Issue 的评论里）、#13（任务完成后实际发放奖励）、#26（对象池接入，与以后的伤害数字有关）。

本记录只整理设计讨论，**没有修改任何代码、配置、场景或预制件**。设计由用户完成，Claude Code 在讨论中给出建议，并按讨论结果整理了参考类图。

## 用户观察与目标

用户询问 Unity 工程目前还缺哪些核心内容。Claude Code 盘点后建议的顺序是先做"任务发奖 + 死亡复活点 + 第二个任务"。用户指出这个顺序有问题：任务奖励无论是金币还是道具，发出去以后都没有地方能看到，所以应该先做背包或仓库这类功能。

目标是在实现之前把背包和发奖的职责划分、存档方式、上限规则、显示方式确定下来，记进 Issue，再由用户自己实现。

## 用户提出的想法

按讨论顺序记录：

1. **先做背包，再做发奖。** 奖励没有地方显示，发奖就没有意义。
2. **最初的背包设想**：玩家持有的道具用 JSON 持久化，只存"物品 ID + 数量"。用户怀疑是否需要背包管理器，因为背包只是用来显示玩家持有的道具，似乎不需要另外做"添加、删除背包物品"。但用户认为管理器还是需要的：每次打开背包时可以通过它重新读取玩家持有的物品；以后有了消耗品，可以在背包里使用，并由它广播信号，通知负责结算消耗品的管理器。
3. **澄清"背包"和"持有道具"的区别**：用户补充说明，自己的意思是"玩家持有的物品"和"背包"相互独立。物品数据不由背包管理，背包只是显示这份数据的 UI。用户请 Claude Code 讲清楚优劣，再自己决定。
4. **选择方案 B**：这个管理器与其叫"背包管理器"，不如叫"玩家持有道具管理器"。选择单独建一个管理器，因为 PlayerMgr 已经太臃肿。
5. **读写方式**：启动时一次读入全部道具，之后需要时从内存取。用户参考了崩铁、原神"登录时获取全部道具，之后从内存取"的表现。
6. **消耗品用事件**：用户认为判断可以放在订阅方的处理方法里，因为广播只是通知"用户点击了使用这个消耗品"，并不表示已经用掉。针对 Claude Code 提出的三点代价，用户的回应是：
   - 失败提示：做一个浮动提示文字类，需要提示时由订阅方通过 UIManager 生成，不需要再发一个事件回来。
   - 成就和统计：在订阅方确认成功喝下之后再修改，就不会出现"没喝成却记了一次"。
   - 没有订阅者时点击无反应：这是开发期间就能发现的问题，不用考虑。
7. **上限规则**：`maxCount` 为 `-1` 表示无上限。无上限的物品不以格子形式显示，例如金币，参考崩铁、原神，单独显示在背包左下角。用户同意用 `itemType == money` 判断是否为货币，`-1` 只表示无上限。`maxCount` 既是单格上限也是总上限，超出时提示溢出、无法再获得。部分溢出时，加到上限、多出的丢弃；用户判断实际很少会碰到溢出。
8. **存档文件**：单独一个文件，用玩家 ID（角色 ID）标识。用户起初打算把所有物品都存进去，没有的数量记为 0；听了 Claude Code 的分析后改为**只存持有的物品，没有记录就当 0**。
9. **其余几项的结论**：
   - 经验不进物品数据，没有争议。
   - 任务物品也放进背包。交付任务时由玩家持有道具管理器从内存中删除，再同步到文件。
   - 每次数量变化都存盘。
   - 背包暂时不做分类页签，布局参考崩铁、原神。UI 可能交给 Claude Code 拼接，用户提供参考并口述细节，正式开始做时再定。
   - 获得提示和浮动提示类等背包做完、实现药水等道具时一起做；以后还会做伤害数字浮动。
   - 这一批先放"使用"按钮的占位。
10. **素材**：暂时使用 UGUI 自带的素材。原型完成后，用户会提供资源商店的包，由 Claude Code 替换素材。
11. **工作流程**：先讨论，讨论完开 Issue，再动手实现。设计由用户自己完成，写完后由 Claude Code 检查、提意见，并按要求修改。用户要求把这次讨论画成类图放进 Issue 作为参考，并说明以后的实现可能和类图有出入。参考图使用用户提供的崩铁背包截图，由用户自己上传到 Issue。

## 辅助分析与建议

Claude Code 读过的文件：`RewardMgr.cs`、`ItemDatabase.cs`、`ItemRewardData.cs`、`RewardSlot.cs`、`MissionItem.cs`、`MissionMgr.cs`、`MissionConfig.cs`、`PlayerMgr.cs`、`PlayerSaveData.cs`、`BaseManager.cs`、`ConfigMgr.cs`，以及 README、STATUS 和当时开着的 Issues。

### 开发顺序

- 最初建议先做"任务发奖 + 死亡复活点 + 第二个任务"。用户指出问题后，Claude Code 承认把 #13 和 #25 拆开排是错的，改为背包在前。
- 补充区分了三种"让玩家看到奖励"的途径：获得提示、HUD 货币、背包面板。指出真正挡在前面的是**背包的数据层**：`RewardMgr.SettlementReward` 里的 `money`、`consumable`、`missionItem`、`stuff` 分支都是空的，原因是发出的东西没有地方可写。
- 建议顺序为"数据层 → 发放 → 显示"。货币和背包格子分开存放是常见做法，但不是行业统一规定。

### 职责划分

- 起初 Claude Code 把"增删一定会发生"作为反对理由，用户澄清后发现这是理解偏差。用户说的"持有数据和背包界面分开"，本身就是常见的数据和显示分离。
- 真正要决定的是**数据由谁持有、由谁修改**，给出三个方案：
  - A：放进 PlayerMgr。
  - B：单独建一个管理器。
  - C：把数据对象公开，各模块直接修改。

  A、B 都可行，不建议 C：堆叠上限、溢出、存盘、通知刷新会写好几份。数据持有者确定后，原来设想的"背包管理器"未必还有职责：打开面板由 UIManager 负责，显示由面板脚本负责。

### 读写方式

- 打开背包时读内存，不读磁盘，与 PlayerMgr 现有的 `saveData` 写法一致。
- 补充说明：崩铁、原神是联网游戏，权威数据在服务器；本项目是单机，内存数据就是权威，JSON 只负责持久化。

### 消耗品的使用

- 起初建议区分"通知"和"请求"：使用是有结果的，例如满血不能喝药，纯广播拿不到结果。列出了三点代价：拿不到结果、只能有一个订阅方、没有订阅者时没有反应。作为替代方案，提出了"按道具类型注册处理者"。
- 用户回应后，Claude Code 同意用事件实现是成立的。补充建议把事件分成两类：
  - "请求使用"：只有一个处理方，负责判断、生效、扣数量、失败提示。
  - "已使用 / 数量变化"：可以有多个订阅者，包括成就、统计和界面刷新。

### 上限与货币

- 建议"是否无上限"和"是否为货币"分开判断，金币相加时注意 `int` 溢出，`exp` 不进物品数据。
- 提出"部分溢出"需要定规则：任务奖励如果整笔拒绝，会导致任务交不掉或奖励丢失。

### 存档

- "没有的也存成 0"有三点代价：新增物品时旧存档仍要补 0、删除的物品会留下无效条目、显示时要过滤数量为 0 的条目。建议只存持有的物品。
- 不确定当前 LitJson 能否直接反序列化 `Dictionary<int, int>`，建议存成列表，或者先写一个存读测试确认。
- 存档类应放在 `Data/Save`，不要命名为 Config。

### 任务物品与 UI

- 交付前先查数量；任务物品不显示"使用"按钮。
- 一笔奖励含多种物品时会连续写几次文件，可以整笔加完再存。这一点作为可选项交给用户决定。
- 仓库不包含 UI 预制件，拼好的背包预制件要在 `ASSET_RESTORE.md` 登记。可以参考崩铁、原神的布局，但不能使用它们的素材。
- 资源商店素材的替换做法：包由用户用自己的账号导入；Claude Code 读取 `.meta` 中的 GUID，修改预制件引用和九宫格设置；替换后需要截图确认；在 `ASSET_RESTORE.md` 记录包名、版本和授权说明。
- GitHub Issue 可以插入图片，但 `gh` 命令行不能上传附件。建议参考图由用户在网页上拖进去，本项目的截图和测试证据放进仓库再引用。

### 核对中发现的待定点

现在的 `MissionStage` 只有 `missionType / targetCount / targetId`，`MissionType` 只有 Battle、Dialogue、Interaction，没有"提交物品"阶段。要实现任务物品交付，需要先确定配置方式。

## 实际采纳与用户调整

| 项 | 结论 | 来源 |
|---|---|---|
| 顺序 | 背包数据层在前，发奖和显示在后，与 #13 一起做 | 用户提出，Claude Code 补充数据层和显示的区分 |
| 职责 | 方案 B：新建"玩家持有道具管理器"，负责持有数据、增删查和存档；背包面板只负责显示 | 数据与显示分离是用户的思路；方案对比由 Claude Code 给出，用户选择 B |
| 读写 | 启动时读一次，之后从内存取 | 用户提出，Claude Code 同意并补充单机和联网的区别 |
| 消耗品 | "请求使用"事件，由唯一的订阅方负责判断、生效、扣数量，失败时用浮动提示提示；成功后再发"已使用 / 数量变化"事件 | 事件方案和浮动提示由用户提出；拆成两类事件是 Claude Code 的补充 |
| 上限 | `maxCount` 既是单格上限也是总上限，`-1` 表示无上限；超出时加到上限，多出的丢弃并提示 | 用户提出，Claude Code 提出部分溢出的问题，用户决定规则 |
| 货币 | 按 `itemType == money` 判断，单独显示在背包左下角，不占格子 | 用户提出单独显示，判断方式采纳 Claude Code 的建议 |
| 存档 | 单独文件，用玩家 ID 标识，只存持有的物品 | 单独文件是用户的决定；只存持有的物品采纳了 Claude Code 的建议，替代了用户原来的全量方案 |
| 存盘时机 | 每次数量变化都存 | 用户决定 |
| 任务物品 | 放进背包；交付时由管理器扣除并存盘 | 用户决定；交付前查数量、不显示"使用"按钮是 Claude Code 的补充 |
| 背包面板 | 不分页签；物品格子列表、右侧详情、左下角货币；使用按钮本次只做占位，点击后打印日志 | 用户决定，参考崩铁背包截图 |
| 素材 | 先用 UGUI 自带素材，以后换成资源商店素材 | 用户决定 |
| 本次不做 | 使用消耗品、浮动提示、伤害数字、分类页签 | 用户决定 |

- **按道具类型注册处理者**：用户选择用事件实现，这条建议作为历史建议保留。
- **整笔奖励加完再存一次**：用户决定每次变化都存，这条没有采用。
- **LitJson 字典还是列表**：留到实现时由用户决定。
- **任务物品交付的配置方式**：待定，需要在实现交付前决定。

## 论文素材与证据入口

可用于"需求分析 / 系统设计"中背包与奖励模块的设计取舍，包括：

- 数据与显示分离；
- 持有数据的单一修改入口；
- 单机存档以内存为权威；
- 只存持有的物品；
- 用事件请求消耗品使用，并区分"请求"和"结果"两类事件。

崩铁、原神只作为界面布局和"登录时载入、之后从内存读取"这一表现的参考，不能写成本项目对它们内部实现的了解。论文里背包作为配套模块来写，不作为核心研究内容（口径见 #25 正文）。本记录不包含任何实现或测试结果。
