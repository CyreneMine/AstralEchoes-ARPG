# 道具上限、奖励进背包与任务结算发奖

日期：2026-11-22。工程版本：基于 `a01d545`。

协助工具：Claude Code（检查与解释）。相关 Issue：#25（简单背包与道具表）、#13（任务完成后实际发放奖励）。上一阶段见[记录 44](44-bag-detail-panel.md)。

`PlayerItemMgr`、`RewardMgr`、`RewardSlot`、`MissionMgr` 的改动都由用户编写。Claude Code 只做检查和解释，没有修改这些文件。

## 用户观察与目标

用户认为背包系统除"使用"以外已经完成（销毁不做、使用延后，见[记录 44](44-bag-detail-panel.md) 补充）。Claude Code 对照 #25 指出还有三项没做：

- `maxCount` 上限；
- `RewardMgr` 里非经验类型的分支，没有这些分支时奖励进不了背包；
- `RewardSlot` 名称写死为"金币"。

用户补上了这三项，并接着完成了任务结算发奖（#13）。

## 用户的做法

1. **上限**：`AddItem` 在"已有记录叠加"和"新增记录"两条路径上都截断到 `maxCount`；`maxCount` 为 -1（无上限）时不截断。新增路径截断后，事件里传的也是截断后的数量。
2. **奖励进背包**：`RewardMgr.SettlementReward` 中，经验继续走 `PlayerMgr.AddExp`，其余类型合并为 `default` 分支，统一调用 `PlayerItemMgr.AddItem`。
3. **奖励名称**：`RewardSlot.Init` 改为从道具表读取名称。
4. **任务结算**：`MissionMgr.FinishMission` 在 `!isFinished` 时从配置表取 `itemRewards`，先把任务标记为已完成，再调用 `RewardMgr.SettlementReward`。

## 辅助分析与建议（Claude Code）

| 轮次 | 发现 | 用户处理 |
|---|---|---|
| 1 | 上限判断没有排除 -1：金币的 `maxCount` 为 -1，任何正数都大于 -1，叠加一次金币就会被写成 -1 并存盘。另外，新物品首次加入时没有截断 | 加上 `maxCount > 0` 的条件，新增路径也做截断 |
| 2 | 新物品截断后，事件仍然传请求的数量（例如传 150，实际只存了 99） | 截断时同时修改 `itemCount`，事件传出实际数量 |
| 3 | 任务结算没有会出错的地方。建议把 `isFinished = true` 移到发奖之前：如果以后加入"获得道具时检查任务"一类的逻辑，可以防止发奖过程中同一任务被重复结算 | 用户采纳："有道理，已采纳" |

其他说明：
- 任务 0 当前配置的奖励只有经验（`itemId 0`、`count 100`），完成后背包不会有变化。要测试任务奖励进背包，需要在配置里加入金币或药剂。
- 上一轮测试中的"打怪或完成任务"一项，是在任务结算写好之前测的，当时通过的只有打怪掉落。

可选的整理（用户没有处理，不影响运行）：
- `AddItem` 中重复查询配置，可以先查一次存进局部变量；
- 超出上限时没有输出日志（#25 原定先用日志代替提示）。
