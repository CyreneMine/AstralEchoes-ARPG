## 辅助分析与建议（Claude Code）

### 随机抽取

- **用户的写法**：循环 `Mathf.Min(3, 候选池数量)` 次，每次随机取一个下标，抽到用过的下标就重抽。用 `Min` 是为了在候选池不足 3 个时循环也能结束。
- **开销**：候选池有 n 个、抽 3 个时，期望的随机次数是 n/n + n/(n−1) + n/(n−2)。n = 50 时约 3.06 次；n = 3 时是 1 + 1.5 + 3 = 5.5 次。只有要抽的个数接近候选池大小时，重抽才会明显变多，两种情况都不会卡。
- **常见的另一种做法**：部分 Fisher–Yates 洗牌。把候选池复制一份，只洗前 3 个位置，随机次数固定为 3，不需要重抽。用户选了自己的写法。
- **对外暴露**：候选列表用私有字段，面板通过只读属性读取。Claude Code 提醒过，属性类型可以改成 `IReadOnlyList`，防止外部代码 `Clear` 或 `Add`。用户还没改，可改可不改。

### 选择次数

候选池数量和选择次数是两个数，变化时机不同：

| | 含义 | 什么时候变 |
|---|---|---|
| `ChoiceCount` | 还能选几次 | 打完战斗节点加 1，选一次减 1，全灭时清零；要随保存点保存（#32） |
| `poolCount` | 候选池里还剩几个没生效的 Buff | 选中时减 1，Buff 到期回到池里时加 1 |

- **扣次数的位置**：`AddBuff` 的意思是“让这个 Buff 生效”。控制台加 Buff、以后读档恢复（#32）都会调用它，在里面扣次数会误扣。建议单独写一个选中方法，`AddBuff` 只负责让 Buff 生效。用户采纳，写成了 `SelectBuff(id)`。
- **选中时的校验**：`SelectBuff` 先确认 id 在本次候选里。用户第一版用 `buffConfigs[id]` 取配置，又把 id 当成了下标，和记录 50 里的 `RemoveAt(id)` 是同一类问题。现在 id 正好是 0、1、2，所以碰巧能用。建议改用 `GetBuffConfigById`，用户采纳。
- **为什么用事件**：次数是在战斗那边加的（打完战斗节点），关心次数的是 GamePanel 的按钮和面板。不用事件的话，要么让战斗代码直接调用 UI，要么让 GamePanel 每帧读一次次数。用了事件，BuffMgr 只负责通知，不需要知道谁在听，这就是观察者模式。反过来，如果次数只在面板自己的点击里变化，面板点完自己刷新就够了，不需要事件。
- **订阅方要注意两点**：
  - GamePanel 隐藏后会被 UIManager 销毁，要在 `OnDestroy` 里取消订阅。
  - 每次重新创建 GamePanel 时，先读一次 `ChoiceCount`，因为它可能错过了之前发出的事件。
- **`ClearAll`**：全灭、副本结束时要把次数清零、清空候选，并发出事件。用户采纳。
- **事件名**：第一版叫 `onBuffCountChange`，容易读成“Buff 的数量”，建议改为 `onChoiceCountChange`。用户采纳。

### 被撤回或修正的分析

- **撤回的建议**：Claude Code 建议在 `SelectBuff` 开头判断，`choiceCount <= 0` 时直接返回。用户指出，次数为 0 时 GamePanel 的按钮是隐藏的，面板打不开，由 UI 入口把关就够了。按用户的约定，这条撤回。
- **修正的说法**：用户同时说“就算打开了 面板里面也是0个buff”，这一点和代码对不上。`SelectBuff` 选完会马上重新抽取，所以最后一次选完时，候选又是满的。由此留下一个前提：最后一次选完后要关闭面板，或者点击后先看 `ChoiceCount`，为 0 就关闭。用户的 `BuffOption` 每次选完都关闭面板，这个前提已经满足。
- **候选真正为 0 个的情况**：次数大于 0，但所有 Buff 都在生效，候选池是空的。这就是计划用浮动文字提示的情况。

### 控制台（Claude Code 修改）

- **Buff 页左下新增“三选一”区域**：
  - 显示剩余选择次数、候选数量和候选池数量。
  - 3 个候选按钮显示 `RandomBuffs` 里每个候选的名称和加成，点击调用 `SelectBuff`。空的位置根据情况显示“先抽一次”“空位”或“候选池为空”。
  - “次数 +1”调用 `AddChoiceCount`，“抽一次候选”调用 `StartRandomBuff`。
- **和游戏入口一致**：次数为 0 时，控制台不调用 `SelectBuff`。
- **直接 `AddBuff`**：左侧列表直接 `AddBuff` 时不扣次数。如果加的正好是本次的某个候选，再点这个候选会被控制台拦截，否则会重复 `AddBuff`，在 `timers.Add` 抛异常。正常流程里候选只能通过 `SelectBuff` 生效，不会出现这种情况。
- **订阅者出错时**：订阅 `onChoiceCountChange` 的对象如果在 Invoke 时出错，异常会从 BuffMgr 的方法里抛出来。控制台会捕获它，并在提示栏写出调用前后的次数，方便判断是哪个订阅者出的错。
- **不订阅次数事件**：控制台每次刷新时直接读取次数和候选。事件有没有按时触发，由自动检查负责。
- **自动检查新增“三选一”一组**，检查结束时用 `ClearAll` 回到初始状态：
  - 按事件的实际类型订阅，无参事件和带次数参数的事件都支持。
  - 次数为 0 时可以抽，但不能选；然后加两次次数。加次数、选中和 `ClearAll` 后，事件各触发一次；带参数时，参数等于新的次数。
  - 连续抽 200 次，检查每次的数量都是 min(3, 候选池)，候选互不重复，都不是生效中的 Buff，候选池里的每个 Buff 都至少被抽到一次。
  - 选中第 1 个候选后：它生效，次数减 1，候选池减 1，加成增加；之后的候选里没有生效中的 Buff。
  - `SelectBuff` 传入不在候选里的 id，或者配置表里没有的 id：不扣次数，状态不变。
  - 直接 `AddBuff` 不扣次数；已经直接添加的候选，再点选中会被拦截。
  - 全部 Buff 生效后候选池为空，这时抽取得到 0 个，次数保留。
  - `ClearAll` 后：次数清零，候选清空，生效列表清空，候选池恢复为全部配置。
  - Buff 页截图时额外加两次次数、抽一次，截图里能看到候选。

### 面板脚本审查（都已由用户修复）

**1. GamePanel 没有退订次数事件**

- 过程：
  - `BuffPanel.ShowMe` 会隐藏 GamePanel，UIManager 随后把它销毁；关闭 BuffPanel 时再新建一个 GamePanel，它又订阅一次。
  - 旧 GamePanel 的订阅还留在 `BuffMgr` 的事件里。选中时事件先调用旧的那个，访问已经销毁的 `btnBuff` 时抛出 `MissingReferenceException`。用户实测时遇到的就是这个错误，堆栈指向 `GamePanel.cs` 的 `OnBuffChoiceChange`。
- 为什么对象销毁了还能被调用：`Destroy` 销毁的是 Unity 那边的物体，C# 对象只要还被事件里的委托引用，就不会被回收；只有访问到 Unity 组件时才会报错。
- 后果：
  - Buff 其实已经选上了，因为 `SelectBuff` 最后才发事件；
  - 排在后面的新 GamePanel 收不到通知；
  - `ClearAll` 是先发事件、再 `player.ClearBuff()`，这个异常会让加成清不掉。
- 这在观察者模式里叫“失效监听者问题”（lapsed listener problem）：发布者活得比订阅者久，订阅者销毁时忘了退订。如果处理方法里不碰 Unity 组件，就不会报错，只会悄悄占着内存。
- 修复：订阅和退订成对，跟着订阅者的生命周期走。用户改为在 `OnEnable` 里订阅、在 `OnDisable` 里退订。

**2. 新建的 GamePanel 没有按当前次数刷新**

- 第一版在 `Init` 里先把 Buff 按钮隐藏。有次数时打开面板、不选直接关闭，或者有 2 次、选了 1 次，新的 GamePanel 都会把按钮藏起来，剩下的次数就选不了了。
- 用户删掉这行后，按钮在预制体里本来就是隐藏的，结果一样；改成“次数大于 0 就显示”后，次数文字又停在预制体的默认值“剩余强化次数:3”。
- 原因：订阅只能收到之后的变化，创建之前已经有的次数要靠自己读一次。最终用户在 `Init` 里调用 `OnBuffChoiceChange(BuffMgr.Instance.ChoiceCount)`，初始化和收到事件走同一段显示代码。

**3. 候选池为空时打开 BuffPanel，GamePanel 会丢失**

- 条件：还有次数，但所有 Buff 都在生效。
- 过程：`BuffPanel.ShowMe` 让 GamePanel 开始淡出；下一帧 `BuffPanel.Init` 抽出 0 个，立即隐藏自己并 `ShowPanel<GamePanel>()`。这时字典里还是那个正在淡出的 GamePanel，`ShowPanel` 直接返回它、不调用 `ShowMe`，淡出结束后被销毁。
- 后果：HUD 消失；打开面板时禁用的 `inputActions` 要靠 `GamePanel.ShowMe` 恢复，所以玩家也动不了。
- 修复：用户在 GamePanel 的按钮里先判断 `poolCount`，为 0 时不打开面板（TODO：浮动文字）。`BuffPanel.Init` 里“抽出 0 个就关闭”的分支现在走不到了。

**4. 小问题**：`BuffPanel` 生成卡片时把实例赋回了 `optionObj`，第一次之后复制的是上一张卡片。运行结果没错，但读起来像 bug。用户改成了局部变量。

**BasePanel 的修改（用户自己加的）**：淡入淡出期间 `CanvasGroup.interactable = false`，结束时恢复。
- `interactable` 只禁用按钮这类控件；`blocksRaycasts` 仍为 true，淡出中的面板依旧挡住点击。
- 背包、任务、Buff 三个全屏面板打开时都会隐藏 GamePanel、关闭时再新建一个，新面板淡入期间不能点，所以 STATUS 里“淡出约 0.2 秒内重开同一面板会丢失面板”通过点按钮已经很难触发。
- 代码里连续调用“先隐藏、再显示”的情况拦不住，第 3 条就是这种。
- 以上是静态分析。

## 实际采纳与用户调整

写这份记录时，工作区里 `BuffMgr` 的写法如下：

- `choiceCount` 是私有字段，对外只读的 `ChoiceCount`；`randomBuffs` 是私有字段，对外的 `RandomBuffs` 仍是 `List`。
- `event UnityAction<int> onChoiceCountChange`。
- `SelectBuff(id)`：id 不在 `randomBuffs` 里就返回；否则次数减 1、调用 `AddBuff(id)`、重新 `StartRandomBuff()`，最后发出事件。
- `AddChoiceCount()`：次数加 1，发出事件。
- `StartRandomBuff()`：先清空候选；候选池为空时直接返回（TODO：浮动文字）；否则按重抽法抽 min(3, 候选池) 个。
- `AddBuff(id)`：不再扣次数。
- `ClearAll()`：在原来的基础上，把次数清零、清空候选，并发出事件。

未采用：
- 在 `AddBuff` 里扣次数；
- 在 `SelectBuff` 里判断次数为 0；
- 部分 Fisher–Yates 洗牌；
- `IReadOnlyList`（可改可不改）。

面板脚本（审查后的最终版本）：
- **GamePanel**：
  - `OnEnable` 订阅 `onChoiceCountChange`，`OnDisable` 退订；
  - `Init` 里调用 `OnBuffChoiceChange(ChoiceCount)`，按次数显示或隐藏 Buff 按钮，并写“剩余强化次数”；
  - Buff 按钮：候选池为空时不打开面板（TODO：浮动文字），否则打开 BuffPanel、禁用玩家输入。
- **BuffPanel**：
  - `ShowMe` 隐藏 GamePanel，`timeScale` 设为 0；`HideMe` 结束时恢复 `timeScale` 和光标，并重新显示 GamePanel；
  - `Init` 抽一次候选，按候选生成 `BuffOption`；右上角关闭按钮。
- **BuffOption**：显示名称和描述，按 Buff 类型加载 `Icon/Buff/0～2`；点击调用 `SelectBuff`，然后关闭面板。
- **BasePanel**：淡入淡出期间 `interactable = false`。

## 论文素材与证据入口

- **随机不重复抽取**：重抽法和部分洗牌的对比，以及期望次数的计算（n = 50 时约 3.06 次，n = 3 时 5.5 次）。
- **区分两个计数**：选择次数和候选池数量的变化时机不同，存档要求也不同。
- **接口职责**：`AddBuff` 只负责让 Buff 生效，`SelectBuff` 表示“玩家做了一次选择”。读档和调试可以直接复用 `AddBuff`，不会误扣次数。
- **观察者模式的适用条件**：状态的修改方和关心方离得远（战斗 → UI）时用事件；状态只在同一个面板里变化时不需要。
- **入口把关的取舍**：次数为 0 的拦截放在 UI 入口，管理器不重复判断，这是用户的约定。
- **失效监听者问题**：面板会被销毁、管理器一直存在时，订阅和退订必须成对。可以用这次的报错堆栈说明：Buff 已经选上了，只有通知这一步断了，后面的订阅者也收不到。
- **状态和事件要配合使用**：事件只传达变化，新建的订阅者要先读一次当前状态。初始化和收到事件走同一个方法，显示逻辑只写一处。
- **淡入淡出期间禁止点击**：用 `CanvasGroup.interactable` 挡住淡入淡出期间的重复操作，同时说明它挡不住代码里连续调用“先隐藏、再显示”的情况。
